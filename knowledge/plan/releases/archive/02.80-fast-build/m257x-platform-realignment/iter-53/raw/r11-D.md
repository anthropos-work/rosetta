### B1 — `gotenberg.md` states the wrong PURPOSE for the only Gotenberg call sites: the PDF is a throwaway text-extraction intermediate, never displayed or stored
- **Anchor:** `corpus/services/gotenberg.md:7` — *"In the Anthropos platform it exists for one consumer: the backend service uses it to render user-uploaded documents into PDFs **for downstream display and storage**."*
- **Why it is false:** I enumerated **every** `ConvertToPDF` caller in `app` (`grep -rn "ConvertToPDF" --include='*.go'` → exactly two call sites, plus the definition):
  - `app/internal/web/backend/coursebuilder/extract.go:77-81` — converts an office doc to PDF and **immediately** feeds the bytes to the text extractor: `return converter.ConvertFromReader(bytes.NewReader(pdf), "application/pdf")`. The PDF variable never leaves the closure.
  - `app/internal/worker/tasks/user_import_resume_2d.go:68-74` — converts a DOCX **only on the OCR fallback path** (`ocrInput = pdfBytes`), then hands it to `h.ocrClient.OCRProcess`. Log line: *"DOCX converted to PDF for OCR"*.

  Neither site persists the PDF, writes it to storage, or returns it for display. The enclosing function in `extract.go` is `newRoutingExtractor(gotenbergURL string) TextExtractor` (`:46`) — a **text extractor**, not a renderer. So the documented role ("render … for downstream display and storage") is the mechanism described backwards; the real role is *format normalisation so text/OCR extraction can run*. A reader debugging "where do the converted PDFs get stored?" is sent to the storage service for an artifact that does not exist.
- **Confidence:** high
